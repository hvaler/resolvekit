# Deployment

How ResolveKit's two services are deployed on Render, in which order, and what to check when a version changes. For
every environment variable see [Configuration](../technical/configuration.md); for day-to-day operation see the
[Runbook](runbook.md).

`npm run demo:check` passed every line except the empty reserve of the standard case (see
[Runbook](runbook.md#dispute-rotation-and-the-reserve)). `demo:check` cannot prove which commit is live. The previous
recorded deployment was `bdd1fd9` on 19/10, both services, MeterMCP first and ResolveKit by hand.

## Services

Both services come from [`render.yaml`](../../render.yaml) (a Render Blueprint).

| | `resolvekit-metermcp` | `resolvekit` |
|---|---|---|
| What it is | The metered MCP gateway (`apps/metermcp`, `METERMCP_MODE=hosted`) | The web app and its API on one origin (`apps/server`, `RESOLVEKIT_MODE=hosted`) |
| Build | `npm ci` | `npm ci && npm run build` |
| Start | `node apps/metermcp/src/main.ts` | `node apps/server/src/main.ts` |
| Health check | `/healthz` | `/healthz` |
| Plan, region, runtime | `starter` (0.5 CPU, 512 MB), `oregon`, Node `24.19.0` | same |
| Disk | 1 GB at `/var/data`: the SQLite ledger and the daily budget cap | 1 GB at `/var/data`: see [Backup and recovery](backup-and-recovery.md#what-each-service-keeps) |
| Auto-deploy in the blueprint | `autoDeployTrigger: commit` | `autoDeployTrigger: commit` |
| Public routes | `/mcp`, `/approved`, `/cancelled`, `/health`, `/healthz` | the web app, `/api`, `/healthz` |
| Internal routes | `/agent/mcp` and the admin routes `/sessions…`, reached only from `resolvekit` over Render's private network with the admin token | `/api/ops/*` (operator token), `/api/paypal/webhook/<key>` (PayPal) |

`resolvekit` gets two values from MeterMCP through `fromService`: `METERMCP_URL` (MeterMCP's private `host:port`) and
`METERMCP_ADMIN_TOKEN` (generated by Render on MeterMCP). `RESOLVEKIT_SESSION_SECRET` is generated by Render.
`PORT` and `RENDER_EXTERNAL_URL` are set by Render. Secrets are `sync: false`: Render asks for them when the
Blueprint is first created.

Both services refuse to start in hosted mode unless `PAYPAL_ENV=sandbox` (or `live` with
`RESOLVEKIT_ALLOW_LIVE_PAYPAL=yes-real-money`, which the blueprint never sets). Nothing has run against live PayPal.

## Order: MeterMCP first, then ResolveKit

ResolveKit is MeterMCP's client; MeterMCP never calls ResolveKit (it only redirects a buyer's browser to an allowed
`return_to` origin). A ResolveKit build can rely on MeterMCP routes, tools or ledger columns added in the same commit
(for example the private `/agent/mcp` endpoint, `open_budget`'s `fail_first` and `return_to`, the admin
`/sessions/<id>/reconcile` route). So:

1. Deploy `resolvekit-metermcp`. Wait until Render shows it live and `GET https://<metermcp host>/healthz` answers 200.
   Look in its log for `MeterMCP on http://0.0.0.0:…` and no `ledger migration failed`.
2. Deploy `resolvekit`. Wait for `/healthz`, then look in its log for `Hosted mode · …`, the bound cases, and the
   warm-up lines (`warm-up · case … · done | cached | skipped`).
3. Run `npm run demo:check` (see [Runbook](runbook.md#the-operators-check-npm-run-democheck)).

The blueprint itself has no explicit order: `fromService` creates a dependency for values, not for deploys.

### Auto-deploy on or off

The blueprint sets `autoDeployTrigger: commit` on both services, so a push to the deployed branch starts both deploys
at once and the order above is not guaranteed. The practice used on 19/10 was: deploy MeterMCP first, then ResolveKit
by hand, and the agent follow-ups recommend turning auto-deploy **off** for `resolvekit` (Render dashboard → the
service → Settings → Auto-Deploy, or `autoDeployTrigger: off` in the blueprint). **Pending:** the blueprint still says
`commit` for both; whether the dashboard setting was changed is not recorded.

Changing an environment variable on Render (for example a new `BINDINGS_JSON`) restarts that service.

### Downtime

A service with a persistent disk cannot have zero-downtime deploys on Render, and runs as a single instance. During a
deploy about 1–2 minutes of HTTP 502 responses were observed (private evidence, 19/10). Schedule deploys outside
review sessions and say so to reviewers when one is needed.

## First deploy (summary)

1. In Render: **New → Blueprint**, pick the repository; Render reads `render.yaml`.
2. Enter the `sync: false` values. Both services need the PayPal **sandbox** seller app (`PAYPAL_CLIENT_ID`,
   `PAYPAL_CLIENT_SECRET`). `resolvekit` also needs the model keys, the identity app
   (`PAYPAL_IDENTITY_CLIENT_ID` / `_SECRET`, a different sandbox app owned by another sandbox business account), the
   webhook (`PAYPAL_WEBHOOK_ID`, `PAYPAL_WEBHOOK_KEY`), `BINDINGS_JSON` and `RESOLVEKIT_OPS_TOKEN`. MeterMCP also needs
   `DEMO_CODE` and `METERMCP_RETURN_ORIGINS` (ResolveKit's public origin, set by hand).
3. Deploy in the order above, then sign in once as the merchant and create the reviewer invite
   ([Accounts and permissions](../user-guide/accounts-and-permissions.md)).

Start-up refuses, and the service does not start, when: `PAYPAL_ENV` is not `sandbox` (or is `live` without `RESOLVEKIT_ALLOW_LIVE_PAYPAL=yes-real-money`, which is never set); `RENDER_EXTERNAL_URL` is
missing or not https; `PAYPAL_IDENTITY_CLIENT_ID` equals `PAYPAL_CLIENT_ID`; `PAYPAL_WEBHOOK_ID` does not look like a
webhook id or comes without a valid `PAYPAL_WEBHOOK_KEY`; `RESOLVEKIT_OPS_TOKEN` is not 32+ URL-safe characters;
`BINDINGS_JSON` (or the bindings file) is invalid; `accounts.json` or `sellers.json` is unreadable; the web build is
missing; on MeterMCP, `METERMCP_ADMIN_TOKEN` is shorter than 32 characters, the public URL is not https,
`METERMCP_BUDGET` / `METERMCP_MIN_BUDGET` / `METERMCP_RETURN_ORIGINS` are invalid (`METERMCP_MIN_BUDGET` above
`METERMCP_BUDGET` included; the blueprint's 5.00 / 0.50 pass), or the ledger cannot be migrated.
A missing `METERMCP_ADMIN_TOKEN` on `resolvekit`, a missing `DEMO_CODE` on MeterMCP or a short session secret only log
a `WARNING` (agent runs stop as `meter_unavailable`; no budget can be created; sign-ins end on every restart).

## Updates, rollbacks and migrations

### MeterMCP ledger migration

At start MeterMCP opens `metermcp.sqlite` (WAL mode), creates the tables if they do not exist, and adds the columns
introduced after the first deploy (`fail_first`, `return_to` on `sessions`). The columns are added in **one
transaction**: either all are added or none is. If the migration fails, it is rolled back, the log says
`ledger migration failed, rolled back (nothing changed): …`, and MeterMCP exits without starting
(`apps/metermcp/src/ledger.ts`, `apps/metermcp/src/main.ts`). An up-to-date ledger changes nothing.

The code comment says the previous deploy keeps serving when the new one cannot migrate. How Render handles a failed
start of a service with a disk, and whether the previous version keeps or resumes serving, was not checked or tested
here (**Pending**). Plan for MeterMCP being down until you roll back or fix the cause.

### ResolveKit data files

The server's stores on `/var/data` (JSON and JSONL files, see
[Backup and recovery](backup-and-recovery.md#what-each-service-keeps)) carry no format version. There is no migration
step: new code reads the existing files. Some files are checked at start (`accounts.json`, `sellers.json`, bindings:
unreadable stops the start); others are read leniently: an unreadable `intents.json`, `analysis-inputs.json`, `recheck-verdicts.json` or
`reserve-position.json` is moved aside as `<file>.corrupt-<time>`, logged and reported, and the store starts empty. Compatibility
of an older version with files written by a newer one was not tested (**Pending**).

### Rolling back

Use Render's rollback to a previous deploy, service by service, **ResolveKit first, then MeterMCP** (the reverse of the
deploy order), so ResolveKit never runs against an older MeterMCP than the one it was built for. Before rolling back
MeterMCP over a ledger migration, know that the added columns stay in the database; an older MeterMCP reading a
migrated ledger was not tested (**Pending**). Take a copy of the disks first if the data matters
([Backup and recovery](backup-and-recovery.md)).

### Before and after every deploy

| When | Check |
|---|---|
| Before | No agent run in progress and no evidence send being made (a stop gives agent runs 20 s to end as `interrupted` and settle; see [Runbook](runbook.md#restarts-and-shutdown)). Reviewers warned if it is during a review window |
| Before | `render.yaml` and the dashboard agree on the values you expect (the dashboard wins for `sync: false` values) |
| After MeterMCP | `/healthz` 200; no `ledger migration failed` in the log; `TEST SWITCH` absent from the log unless intended (`METERMCP_FAIL_FIRST` must not be set on the hosted service) |
| After ResolveKit | `/healthz` 200; `Hosted mode · … PayPal sign-in on · PayPal webhook on · ops check on`; warm-up lines; then `npm run demo:check` |
